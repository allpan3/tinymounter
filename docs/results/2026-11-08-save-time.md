# Save time kept on the server, 2026-11-08

## Outcome

The fix for the kept-file status defect in the [release checks](2026-11-08-release-checks.md#kept-file-status-after-a-local-save)
works in the signed VM app. After an upload's last write, the app sets the server file's
LastWriteTime to the modification time that macOS reported, so the catalog and the local file
agree and a kept file becomes Available offline. This passed for:

- an online save
- an offline save that uploaded after the reconnect
- an offline save and an offline new file, with an app quit and an extension kill before the
  reconnect
- a Finder copy of an old file
- an interrupted 1 GiB upload that continued after a retry

M23/M25 longer, shorter and empty saves, Finder file Replace and folder Replace pass.

Two limits remain, both from before this fix:

- **After a one-sided connection loss, a resumed upload is refused** with "Text file busy" until
  the server drops the old session. Samba kept the old open with DENY_ALL, and its TCP keepalive
  was 118 minutes away.
- **No automatic retry ran within 60 s** after the old session went away. Retry Pending Changes
  finished the upload.

`Tools/run-checks.sh` in the VM at the fix commit: passed. 525 tests, one optional skip, no
failures, no Swift warnings; SET_INFO 9, edit status 91, folder-create status and CCM 7,205
cases passed.

## Setup

- Client: VMPal `macOS VM 1`, macOS 27.0.1. The fix was built unsigned with bundle
  `dev.tinymounter.releasecheck`, signed on the host with the 0.2.0 entitlements, and installed as
  `~/Applications/TinyMounter-SaveTime.app`.
- Server: VMPal `TinyMounter Samba Test`, Samba 4.19.5-Ubuntu. A disposable account and share
  with a password generated inside the VMs. Global settings unchanged. All of it was removed
  afterwards and `smb.conf` restored byte-for-byte.
- Offline: an `iptables` rule on the fixture sent a TCP reset for port 445 from this VM only, so
  other clients and accounts were not affected.
- Times: local times from `os.stat` in a File Provider-aware reader; server times from
  `stat -c %.9Y` on the fixture.

### Findings from the first signed build

The first signed save showed Samba refusing the SET_INFO with `STATUS_ACCESS_DENIED`. The upload
and overwrite handles asked only for write-data access, and FileBasicInformation needs
FILE_WRITE_ATTRIBUTES. The upload succeeded and the refusal was logged, as designed. The fix
commit adds that access; the file saved with the first build stayed Update in progress, as
before the fix.

After the re-signed build was installed, macOS dropped its connections with the kernel reason
`NECP`. Turning the app's Local Network switches off and on fixed it. This is a VM artefact of
replacing a signed app at the same path, not an app defect.

## Correctness and limits

- **Rounding.** The app rounds the time to whole microseconds, because libsmb2 encodes and
  decodes SMB times in microseconds. Every server time above is the local time rounded to the
  nearest microsecond. The largest difference measured was 0.41 µs; the unit test bounds it at
  0.75 µs before 2038 and under 1 µs up to 2100, within `OfflineState`'s 1 µs tolerance.
- **SET_INFO failure.** A refused SET_INFO is logged with its errno and NT status, and the
  upload succeeds with the server's own time; the file then shows Update in progress, as before
  the fix. A lost connection fails the close that follows, so the upload is retried as before.
- **Interruption method.** The fixture rule reset only the client's side. A real network loss
  can leave the server's side open in the same way. The 0.2.0 release check stopped smbd, which
  closes both sides, and its upload finished by itself.
- **Not covered:** a real NAS, Preview saves, and a server that rejects FILE_WRITE_ATTRIBUTES on
  create.
