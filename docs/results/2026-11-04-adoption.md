# Single-client adoption, 2026-11-04

On 2026-11-04 the user adopted the single-client transport and accepted writable partial reads
at a median paired ratio of 0.725 against native SMB. The 0.90 target stays the improvement
goal. The user also approved installing the merged build on the physical Mac with Start Fresh.
This record covers the changes made for that adoption and their VM checks. The evidence behind
the decision is in the [candidate validation](2026-11-04-candidate-validation.md).

## Outcome

- **Normal builds enable folder organization and Delete Permanently….** `deletionEnabled` stays
  false, so ordinary Finder deletion and Finder Replace are still refused.
- **Retry now continues an interrupted permanent deletion.** Before this change, Retry for an
  unsettled record required the ordinary deletion gate. With only the custom command enabled,
  an interrupted request showed "Waiting to continue deletion" and offered only Stop Deleting.
- **Undoing a refused rename now clears it.** A folder rename with a stale base stayed pending
  in macOS forever, even after the user restored the original name in Finder.
- All 658 tests and the required VM checks pass. Nothing was installed on the physical Mac.

## Defects found and fixed

**Interrupted permanent deletion.** Only an enabled route can admit a deletion record, so Retry
now continues unsettled records when either deletion route is enabled. Launch recovery still
only settles records; continuing a request remains an explicit Retry.

**Refused rename with a stale base.** A file was added to a fixture folder on the server, and
the folder was renamed in Finder about 20 s later. The app refused the rename with
`versionChanged` before any server request, which is correct. macOS then throttled the change
permanently. Renaming the folder back in Finder resent the same stale base, and each retry,
including after an app restart, failed again. Settings did not list the item, and the pending
system item blocked Delete Permanently in that location. A rename or move whose name and parent
already match the catalog row now completes with the current item and sends nothing to the
server.

## VM checks

Setup: macOS VM 1, macOS 27.0.1 (26A434), the signed `dev.tinymounter.offlinecheck` test
identity, and the disposable Linux Samba fixture. The builds are normal builds with no test
hooks. The baseline differs from the candidate only in the folder and permanent-deletion gates.
These are correctness checks, with no performance claim.

| Check | Result |
| --- | --- |
| Baseline context menu on a folder | No Delete Permanently… |
| Baseline folder rename | Finder shows the new name, but it stays pending; the server name is unchanged |
| Candidate replaces the baseline | macOS replays the pending rename, which completes on the server |
| Candidate context menu, rename and confirmation | Delete Permanently… appears; the rename completes on the server; Cancel leaves the folder and its 3 files unchanged |
| Undo of a refused stale-base rename | Fix build: `rename_unchanged`, no system pending items remain in the location |
| Interrupted permanent deletion | The app was killed after 25 of 401 files were deleted. After relaunch, Settings shows Retry and Stop Deleting. Retry deletes the rest, the record clears and the other entries stay unchanged |
| `Tools/run-checks.sh` | 658 tests, 2 optional skips, no failures and no Swift warnings |

In this in-place test upgrade, an unchanged folder kept the baseline's item metadata, so Finder
did not offer Delete Permanently… for it until the folder changed. A Start Fresh installation
has no earlier items, so it is not affected.

## Installation preflight

A read-only `fileproviderctl dump` of the installed provider on the physical Mac shows one
domain with 10,856 synchronized entries and one pending item: a local Finder deletion of one
file, which the installed build refuses and macOS throttles. There are no pending uploads.
The app's own pending-change records could not be read from outside the app, because macOS
privacy protection blocks reading the app container. The installed build's Remove Location
refuses removal while app records are pending, so removing the location in that build is
the final check.

The new catalogs have a column that the installed build's catalogs lack. If the new build opens
an earlier catalog, the location shows as catalog unavailable. Removing the location in the
installed build before the update avoids that state.

## Remaining limits

- Writable partial reads stay below the 0.90 target.
- A save after a POSIX whole-file read becomes a conflict copy; the original is kept.
- A rename refused for a stale base stays pending in Finder until the user restores the
  original name. Settings does not list it, and it blocks Delete Permanently… in that location.
- Ordinary Finder deletion and Replace remain refused.
- Physical-Mac behavior and performance remain unverified until installation.
- Public distribution still needs the libsmb2 change notices, source provision and relinking
  documentation listed in the [candidate validation](2026-11-04-candidate-validation.md#libsmb2-licence-obligations).
  Local installation does not depend on them.
