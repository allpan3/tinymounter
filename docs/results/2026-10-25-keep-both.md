# Finder Keep Both

Date: 2026-10-25. Decision status: within the accepted M18 create-only scope.

Finder Keep Both now works for files in the final signed VM app, including repeated name
collisions with every original and copied byte verified. New-folder copying and read-only Finder
paste checks also passed. Signed callback checks verified the collision payload and rejection
of unsupported mutations. All 232 VM tests and required checks passed. The fixture is removed,
sharing is restored and the physical-Mac app remains M16.

## Finding and implementation

Setup: macOS VM 1, the signed sandboxed app, a disposable guest loopback SMB fixture and a
4,352-byte incoming file with different contents from the same-name destination. Caches were
reused and uncontrolled. This is a behavior check, with no performance claim. Both the scripted
URL clipboard and normal Finder Copy reproduced error 0 before any create callback.

The signed metadata trials held the backend constant:

| Metadata in an enabled location | Finder Keep Both |
| --- | --- |
| Original read capabilities and read-only file flags | Error 0, no create callback |
| Writable file flags alone | Error 0, no create callback |
| Rename capability, original read-only file flags | New create callback and successful upload |

The successful trial preserved the original bytes and uploaded the incoming bytes under the
system's alternative name. The fix grants rename capability to files and folders only when
changes are enabled. It preserves file-system write flags, the sandbox and all remote mutation
checks. No transport, dependency or saved format changes.

Finder consequently also offers Rename for existing items. General renaming remains unsupported
and returns a permission error. The only remote rename allowed is the already approved initial
name of a folder whose creation receipt proves ownership. This menu limitation avoids expanding
M18 into general rename support just to allow collision copies.

A separate error-contract defect also needed correction. The app formerly returned a bare
filenameCollision error. After a definite collision it now refreshes the parent listing, and
the extension uses Apple's factory with the existing catalog item. If that item cannot be
identified, it returns cannotSynchronize rather than an incomplete collision error. No item
payload or source name is logged.

Regression tests cover changed input after a collision, repeated collisions at alternative
names and refusal to change the name of an uncertain upload. Only a definite collision can
accept another name supplied by the system. An uncertain upload keeps its complete local copy.

## Verification and cleanup

Tools/run-checks.sh passed in the VM with the writable fixture enabled: 232 tests, no skips
or failures, project generation, release CLI, benchmark validation and unsigned app build.
There were no Swift warnings. The final personalized build also compiled without Swift warnings
and passed strict/deep signature verification. It was opened only in the VM.

The final normal signed app passed:

- Keep Both for a 4,352-byte file, then a repeat with the first alternative name already in use.
  Both alternative copies matched the incoming bytes; the original retained its different bytes.
- A new folder with a 3,840-byte child, with matching remote bytes.
- Changes disabled, then Finder Paste of a fresh file. No remote file appeared, and the
  original bytes stayed unchanged.
- Matched before/after recordings, with the same input, original destination and Finder steps.
  The baseline ends at error 0; the final recording shows both files.

Finder offered only Stop and Replace for the tested folder collision, including while Option
was held. Stop preserved the original child. This does not verify Keep Both or merging for folders.

A separate signed archive changed only FileProviderExtension.swift to call the real callbacks
on this disposable location. It verified the existing item's ID, parent, name and size in the
collision error, the cannotSynchronize fallback, and denial of file editing, file rename,
delete and naming an existing folder without a creation receipt. The normal final app contains
no test hooks. A later read-only callback repeat could not run because switching development
registrations returned providerNotFound. Restoring the normal signed registration recovered the
existing location without a reset. The normal signed read-only Finder check above passed; the
separate callback repeat remains unverified. No separate File Provider daemon restart was used.

VMPal reported the VM stopped after the builds, for an unknown reason. The user approved
starting it to finish the checks and cleanup. The temporary mount and input were restored
within the accepted fixture scope. Caches were uncontrolled across this interruption, so these
runs support behavior claims only.

Cleanup removed the disposable location without a saved keep list, both temporary server
entries, hidden mount, input and remote fixture bytes, temporary test apps and source archive.
The root-only snapshot restored exact sharing records, SMB service/override and guest settings.
The local SMB service is unloaded, SMB guest access and guest login are off. The original NAS
was reconnected from its saved URL through macOS, with no password access or remote writes.
The final normal signed app relaunch reports zero locations, catalogs, domains, unknown domains,
failed reconciliation sequences, items, keeps and staging files. One saved share and its native
NAS mount remain; no reader session is open after the relaunch. Cairndex's processes were
preserved after the approved VM start. The clipboard is clear and no test CloudStorage folder
remains. No physical-Mac installation or publication was performed.
